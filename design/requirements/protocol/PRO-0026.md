# PRO-0026: Publication schedule

**Tags**: protocol

## Description

### PublicationSchedule

`PublicationSchedule` specifies the desired timing of a subscription's publications ([PRO-0024](./PRO-0024.md)).

| Variant    | Type                          | Description                                                     |
| ---------- | ----------------------------- | --------------------------------------------------------------- |
| `Periodic` | `PublicationSchedulePeriodic` | Publish periodically.                                           |
| `OnChange` | No payload                    | Publish when a selected sample's value or availability changes. |

### PublicationSchedulePeriodic

| Field               | Type       | Description                                                                                     |
| ------------------- | ---------- | ----------------------------------------------------------------------------------------------- |
| `interval`          | `Duration` | Desired interval between publications.                                                          |
| `phase`             | `Duration` | Desired phase of publications with respect to the clock origin ([PRO-0027](./PRO-0027.md)).     |
| `consumption_delay` | `Duration` | Expected delay from scheduled publication time to consumption time ([PRO-0030](./PRO-0030.md)). |

### Server implementation hints

The next scheduled publication at or after server time `t`, using the schedule in effect at that time, is:

```text
next_publication_time(t) = t + ((phase(t) - t) mod interval(t))
target_time(t) = next_publication_time(t) + consumption_delay(t)
```

### Client implementation hints

Client implementations can estimate the phase and consumption delay as:

```text
consumption_delay(t) = transit_delay(t) + processing_delay(t) + arrival_margin
scheduled_publication_time(j, t) = consumption_time(j) - consumption_delay(t) + client_to_server_clock_offset(t)
phase(t) = scheduled_publication_time(j, t) mod interval(t)
```

For an upcoming consumption event `j`, using estimates available at client time `t`.

## Rationale

In order to minimize the time between sample acquisition and sample consumption, the client needs to be able to control the publication timing.
This means not only the rate needs to be configurable, but also the phase.

In order to let the device predict sample values for their expected consumption time, the client needs to be able to send a publication to consumption duration.
